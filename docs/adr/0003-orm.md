# ADR 0003: Drizzle ORM for PostgreSQL

- Status: Accepted
- Date: 2026-10-29

## Context

BUILD_PROMPTS 2.1 asks for Prisma or Drizzle, decided here. What the API needs from it:

- **Money as `bigint` cents** (CLAUDE.md), handled in code as JS `number`: `@fabric/core` works on safe integers and asserts them. One shop never comes near 2^53 cents (90 trillion dirham).
- **Sync** (ADR 0002): an idempotent push that upserts mutable entities only when the incoming `(updated_at, device_id)` wins (last write wins), assigns `server_seq`, and never overwrites append-only rows.
- **Database-level guards**: triggers that reject `UPDATE`/`DELETE` on `stock_move`, `payment`, `audit_log`, and a trigger that sets `server_seq` from a sequence on every write.
- **Reviewable migrations** committed as SQL, and reads for reports and the integrity check that need plain SQL (sums, CTEs, window functions).
- NestJS 12, ESM, TypeScript strict, Docker images built with `turbo prune`.

Versions on 2026-10-29: Prisma ORM 7.10 stable (8.0 in release candidates); Drizzle ORM 0.45 stable (1.0 in release candidates); Kysely 0.29; TypeORM 1.1; MikroORM 7.2.

## Decision

**Drizzle ORM** (stable 0.45 line) with **drizzle-kit** for migrations and the **node-postgres (`pg`)** driver.

- Schema in TypeScript under `apps/api/src/database/schema/`, one file per feature. Modules import tables from `database` (the dependency rules already allow `modules/* → database`).
- Money and lengths: `bigint(..., { mode: 'number' })`; `server_seq`: `bigserial({ mode: 'number' })`. Values cross into core as numbers and core validates them.
- Migrations: `drizzle-kit generate` writes SQL into `apps/api/drizzle/`, which is committed and reviewed. Triggers, sequences and views go in custom migrations (`drizzle-kit generate --custom`). `make migrate` runs the migrator at deploy and before integration tests. No `push` against a shared database.
- Sync upsert: `insert … onConflictDoUpdate({ target: id, set, setWhere })`, with `setWhere` comparing `(updated_at, device_id)`: last write wins in one statement, no read-modify-write race.
- Transactions: `db.transaction()` for every multi-table write (a sale, its lines, stock moves and the audit row).
- Contracts stay the source of truth for API shapes (`@fabric/contracts`, zod); Drizzle's zod helpers are not used for the API.

## Why not the others

- **Prisma.** It maps a `BigInt` column to the JS `BigInt` type, with no option for `number`. Every money value would need converting at every read and write, and `BigInt` does not serialise to JSON. Its `upsert` has no conditional update, so the sync merge would be raw SQL anyway. It also needs a generate step in dev, CI and Docker. Its migration tooling (drift detection with a shadow database) is more mature, and that is what we give up.
- **Kysely.** A good typed query builder, but no schema or migration generation: we would write both by hand.
- **TypeORM, MikroORM.** Entity and unit-of-work models (change tracking, lazy relations) fit append-only ledgers and explicit SQL less well.

## Consequences

- Drizzle 1.0 changes the migration folder layout and the relational query API. When 1.0 is stable, upgrade in its own change with `drizzle-kit up` and re-run the integration tests. Until then, pin 0.45.x in the catalog.
- Without a shadow database, schema drift is caught by CI instead: run every migration from an empty database, then `drizzle-kit check`, in the integration-test job.
- The BUILD_PROMPTS §1.2 tree's comment "prisma client" for `database/` reads "Drizzle client" from now on.
